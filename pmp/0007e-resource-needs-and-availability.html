资源需求与可用性：先看缺口类型，不是直接加人

核心系统缺审计开发经验，前端 UI 被其他项目占用。先加人？先看数据？本课讲怎么按技能定义资源、按缺口类型选应对方式——技能缺口培训或外包，时间窗缺口调顺序，容量缺口才加人。

看点菜

按需点菜 vs 厨房有几个人手

开餐厅不是先雇人再看做什么菜。先看菜单需要什么技能（炒菜、面点、甜品），再看厨房现在有谁、谁有空。缺的是技能就培训或外包，缺的是时间窗就调排班，缺的是人手才招人。项目资源也一样。

沿案例权衡

客户服务平台：两个缺口，两种应对

整合计划（0007A）排好了。现在一个关键约束浮现：核心系统缺审计开发经验，前端 UI 被其他项目占用到三周后。

01

技能缺口：培训或外包，不是加人

核心系统需要熟悉审计合规流转逻辑的开发技能。团队内部有开发，但没有审计经验。这是技能缺口——不是人不够，是现有的人缺这项技能。应对方式：培训内部开发人员（两周学习审计要求），或者外包给有经验的外部团队。

记忆钩子：技能缺口 = 人有但技能没有。培训或外包，不是加人——加一个也没审计经验的人没用。

02

时间窗缺口：调顺序，不是等

前端 UI 设计师被另一个项目占用到三周后才释放。技能在内部存在——只是在这个时间段不可用。这是时间窗缺口。应对方式：前两个 Sprint 先做不依赖 UI 的后端逻辑，三周后 UI 释放了再接入前端迭代。

记忆钩子：时间窗缺口 = 技能有但时间不对。调 Sprint 顺序，不是干等——等三周不调顺序会让前两周空转。

03

容量缺口：用数据确认，才考虑加人

那什么时候才该加人？当数据显示工作量确实超出现有人员的处理能力——交付时间持续上升、负荷率长期超过 90%、等待队列不断增长。这就是容量缺口。但确认容量缺口必须看数据，不能靠感觉。如果负荷率还在 70% 以下但交付时间在上升，问题可能不是人不够，而是分配不均——调任务分配比加人更有效。

技能缺口
人有但技能没有。培训或外包。加一个没技能的人没用。
时间窗缺口
技能有但时间不对。调顺序。干等会空转。
容量缺口
工作量确实超能力。用数据确认。才考虑加人。
想一想：资源决策做完后，为什么必须写回整合计划？

资源决策改变了时间线——培训延长了核心系统第一阶段、Sprint 顺序调整改变了前端依赖。不写回整合计划，下一次资源评估没有当前数据，相关方看到的是过时的计划。

记忆钩子：资源决策的终点不是"选完了"，是更新整合计划。不回写就留下下一次决策的盲点。
