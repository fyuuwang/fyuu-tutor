资源需求与计划决策：缺口出现时，先看数据而非先加人

整合计划（0007A）已列出工作。现在一个关键约束浮现：核心系统缺审计开发经验，前端UI资源被其他项目占用。本课不教你直接加人——而是从技能需求出发定义资源、对比可用性，在缺口出现时用数据而非直觉做权衡。

看资源地图

资源不是"要几个人"——它的起点是技能，终点是数据驱动的权衡

整合计划说清楚了做什么，但没回答谁来做。资源规划的起点不是"我们缺3个开发"，而是"完成这些工作需要什么技能、这些技能在内部是否可用、不可用时怎么办"。本课的地图就是这条权衡链。

沿案例权衡

客户服务平台：两个缺口，一个数据驱动的答案

0007A 编排的整合计划里，核心审计模块需要阶段交付、前端体验模块需要每两周 Sprint。现在一道约束出现：核心系统缺有审计开发经验的人员，前端 UI 设计师被另一个项目占用到三周后。先加人还是先看数据？

01

按技能定义资源，不按头衔

ECO Task 4 的第一步是"根据需求定义和规划资源"（E01）。定义资源不是写"3个开发+1个设计师"，而是从工作出发倒推技能：核心审计模块需要熟悉合规审计流转逻辑的开发技能，前端体验模块需要在快速原型和高频用户反馈中迭代的 UI 技能。头衔不能替代技能定义。

然后区分：哪些技能内部已有（普通开发、客服领域知识），哪些需要从外部获取（审计合规开发经验、有原型迭代节奏的 UI 设计）。区分可用性和可获得性，才知道缺口在哪里。

技能需求
完成工作所需的能力和经验：审计合规开发、原型迭代 UI。从头衔倒推会漏掉关键的隐性技能。
内部可用 vs 外部需要
内部已有且可释放的 vs 必须从外部获取的。先盘点内部，再规划外部获取方式。

记忆钩子：先问"完成这些工作需要什么技能"，再问"谁有"。不用头衔画资源表。

02

对比可用性：不是所有缺口都需要加人

ECO 要求"管理和优化资源需求与可用性"（E02）。核心系统的审计开发缺人是一个技能缺口——内部有开发，但没有审计合规经验。前端 UI 被占用到三周后是一个时间窗缺口——技能在内部存在，但在需要的时间段不可用。

不是所有缺口都需要加人。技能缺口可以通过培训现有人员或外包解决；时间窗缺口可以通过调整 Sprint 顺序——先把不需要 UI 的后端逻辑在前两个 Sprint 内推进，等三周后 UI 释放了再接入前端迭代。关键是不把"缺口"和"加人"画等号。

记忆钩子：缺口的类型决定应对方式。技能缺口可能是培训或外包，时间窗缺口可能是调顺序。直接加人只适合容量缺口——工作量确实超出现有人员的处理能力。

03

用数据决策，不用直觉

ECO 要求"收集并分析数据以做出明智的项目决策"（E09）。面对资源缺口时，最容易犯的错误是用直觉拍板："我们缺人，加3个"。数据驱动意味着先看三条数据：每条工作项的平均交付时间是否在上升、关键资源当前的负荷率、等待资源的任务积压量。如果数据显示等待时间在上升但负荷率还在 70% 以下，问题不是资源数量而是资源分配——调整任务顺序比加人更有效。

数据驱动
用交付时间、负荷率、等待队列长度等可观测数据判断瓶颈类型，再选择应对方式。
直觉决策
感觉资源不够就加人。没有数据验证瓶颈到底是数量、分配还是技能问题。

记忆钩子：感觉缺人不是数据。先看瓶颈在哪——工作量过多、分配不均还是技能不对——再选应对方式。不是所有缺口都用加人解决。

04

把资源决策写回整合计划

资源决策不是独立的——它直接影响整合计划里的时间线和依赖。审计合规开发的培训需要两周，意味着核心系统第一个阶段的交付时间要调整。前端 UI 三周后才能接入，意味着前两个 Sprint 要做不依赖 UI 设计的后端工作。这些都要写回整合计划并重新沟通。

写回计划不是为了重新审批——整合计划在 0007A 里已经说了要受控维护（E08）。写回是为了让依赖被更新、让风险被记录、让下一个资源决策有当前数据可查。不写回计划，下一次资源评估就是从头猜。

想一想：三个选择——培训内部人员、调整 Sprint 顺序、外包审计模块。你怎么向相关方沟通这个决策？

不是群发邮件。对合规法务解释培训审计开发技能的必要性和时间窗口影响；对产品负责人解释前两个 Sprint 优先做后端的原因；对所有相关方展示一份更新后的整合计划——每个调整都标注了原因、对依赖的影响和下一次复盘的时点。

记忆钩子：资源决策的终点不是"选择完毕"，是更新整合计划并沟通调整。不回写计划就是留下下一次决策的盲点。
